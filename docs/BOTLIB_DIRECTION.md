# Directional movement and obstacle checks

`MovementObstacles` and `BotDirectionalMovement` are independent Java services for the original botlib directional-movement boundary. They do not choose goals, replace game AI, or hardcode weapons. The host owns movement state and elementary actions; these services return immutable decisions.

## Obstacle geometry

`MovementObstacles(AasMovementPredictor.World)` uses the observed defaults `sv_step=18` and `sv_maxbarrier=32`. An overload accepts both values. Its world must supply the composed AAS presence trace, including dynamic entity clipping, and engine point contents.

`barrierJump(MovementInit, direction, speed)` performs at most three standing-presence traces: upward clearance, horizontal forward clearance, and a downward landing. It normalizes direction in XY, ignores Z and measures forward travel over half the input think time. Both the upward clearance and landing height must be at least the step height; equality succeeds. Start-solid traces fail. Partial upward or forward movement can still be sufficient. The landing must report fraction below one, even with a zero step-height setting. The forward calculation preserves the observed float product of speed and think time followed by the double-literal half factor and final float coordinates.

The Java obstacle query is pure. The native barrier helper also sets runtime barrier-jump flag 1 and emits jump followed by a move with the normalized horizontal direction and supplied speed. `BotDirectionalMovement` represents these effects in its decision; another caller must apply those effects itself when choosing to perform the barrier jump.

`gapDistance(origin,direction,entity)` returns zero when no dry gap is found, one when its initial 60-unit downward trace finds no support, or a sampled distance from 8 through 96. It preserves the supplied horizontal direction's scale, discards Z, and makes at most thirteen crouching-presence queries. Forward samples trace down 80 units from 24 units above the retained floor height. Start-solid samples retain the preceding floor. A sample drop greater than 50 units checks contents twenty units below its endpoint; water cancels the gap result, while lava and slime do not. This is the observed query policy, not a new estimate of jump capability.

Seven authored tests cover exact thresholds, partial clearance, normalized versus unnormalized direction, trace bounds, water handling and invalid inputs. A controlled native differential compares 50,000 queries, split evenly between barrier and gap: every return value and query count matches. Another 5,000 barrier scenarios compare all 15,000 trace start/end pairs; all decoded float bits match. Inputs include asymmetric origins, nonunit directions, negative speeds, start-solid replies and boundary fractions. A separate 10,000-case audit varies independent `sv_step` and `sv_maxbarrier` values, including zero and the bounded maximum: all decisions and trace counts match.

`sv_step` and `sv_maxbarrier` are the names requested by the observed native movement setup, with defaults 18 and 32. They are independent of predictor `phys_maxstep`, whose default is 19. The ground-reach forward hull crop also uses `sv_step`: its minimum Z is standing/crouching base −24 plus this value, while maximum Z remains presence top minus ten. Native overrides of `sv_step` to 7 and 19 produce crop minima −17 and −5; changing `phys_maxstep` or `sv_maxbarrier` does not change the crop. `GroundReachMovement` currently fixes the default crop, so its host must explicitly reject nondefault `sv_step` until that helper is parameterized. Gap sampling does not use either obstacle setting. Hosts must refresh immutable services after relevant botlib variables change.

## Directional decisions

`BotDirectionalMovement(Services).move(input,effectiveMovementFlags,direction,speed,type)` returns `Decision(accepted,movementFlags,crouch,jump,Optional<Motion>)`. A motion contains direction and speed. The caller applies returned flags even when a move is refused, then applies successful crouch/jump actions before the optional move. Effective flags are the movement state's retained flags, not merely the latest `MovementInit.moveFlags` input.

The borrowed `Services` interface exposes swimming, ground, barrier, gap and prediction queries. A host composes obstacle methods with `MovementObstacles`, ground/prediction methods with `AasMovementPredictor`, and swimming with the verified engine predicate. The decision layer does not swallow exceptions from unsupported prediction domains.

Observed behavior includes:

- Swimming emits a normalized three-dimensional direction and preserves flags. The caller's direction value is unchanged.
- A ground query sets flag 2 without clearing a retained copy. Grounded processing clears barrier flag 1; a successful barrier restores it and emits jump/move immediately.
- Dry airborne movement normally emits no action and returns success. Retained barrier flag 1 permits an unnormalized supplied move only while vertical velocity is below 50.
- Ground movement uses normalized XY direction. Crouching predicts presence 4; an explicit jump predicts presence 2. A discovered gap adds jumping while retaining any crouch presence already selected. The eventual action bits can contain both crouch and jump.
- Ordinary movement predicts two frames with two command frames; jumping predicts at most thirty frames with one command frame. Frame duration is 0.1 seconds, prediction origin is raised by 0.5, and jump command Z is 400. Requested stop masks are 60 and 61.
- Lava/slime entry or damaging impact refuses movement. An unfinished thirty-frame jump, a gap at a reported landing, or insufficient horizontal displacement also refuses movement. Water entry alone does not refuse it. Landing checks include both a zero-direction support check and the requested direction. The displacement check uses horizontal length, even when its direction differs from the intended move.

Six authored tests cover state transitions, emitted actions, prediction requests, landing checks, exact airborne threshold and invalid/absent results. A 50,000-case differential with unchanged native directional code and controlled public dependencies matches decisions, action bits, motion float bits, movement flags, gap counts and prediction counts. The geometry provider is separately audited above. The oracle varies retained flags, movement types, origin/velocity/direction, signed speed, think time, stop events, landing gaps and predicted duration.

The native directional call does not reliably reject a failed prediction return if output bytes are supplied. Java instead refuses an absent prediction and never acts on undefined output. This explicit safety boundary is separate from the successful-result differential.

## Integration checkpoint and provenance

The directional decision layer is verified against controlled prediction results, and the actual predictor now supports masks 60/61 over its dry geometry domain, including dry-to-fluid stops and damaging impacts. A further 60,000 actual predictor comparisons have no skipped cases or discrete mismatches; numeric error is at most 0.00058. Host integration can compose `predictor::swimming`, `predictor::onGround`, `predictor::predict`, `obstacles::barrierJump` and `obstacles::gapDistance`. The server bridges VM import 550 for both explicit game ABI profiles, reads current obstacle variables and predictor settings for each call, and preserves retained flags and action ordering. Guest tests cover swimming, airborne action preservation and bounds. A strict sixty-second original-qagame q3dm1 audit completes 553 move-to-goal calls and 36 directional calls, with 1,178 moving frames; this demonstrates that local scenario while leaving other maps and movement domains to further validation. Ordinary tilted floor/ceiling contacts, positive unit tilted step landings and presence-hull transitions are supported; downward-facing/non-unit step planes and prediction frames already swimming still fail explicitly. The detailed geometry and clearance audits are recorded in [BOTLIB_MOVEMENT.md](BOTLIB_MOVEMENT.md). The directional swimming path itself is verified and does not invoke prediction. Successful synthetic decisions do not establish autonomous bot movement.

Contracts come from the [published movement declarations](https://github.com/ioquake/ioq3/blob/main/code/botlib/be_ai_move.h), [AAS records and stop events](https://github.com/ioquake/ioq3/blob/main/code/botlib/be_aas.h), and black-box calls into unchanged reference objects. An ignored call-boundary observer redirects the gap/barrier symbols to controlled providers; no engine function body was read as an implementation recipe, copied or translated. Original assets and native reference artifacts are not bundled.
